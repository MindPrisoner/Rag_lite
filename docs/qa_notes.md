# 面试问答笔记

## 1. 你这个项目为什么不用向量检索？
一开始考虑过本地 embedding + 向量检索，但在当前环境里会引入较重的 torch / CUDA 依赖，环境成本和维护成本都偏高。为了先打通完整 RAG 主链路，我先采用 BM25 做轻量检索原型。这样能先把文档加载、分块、检索、生成、服务化和展示完整跑通，后续再升级到向量检索会更顺。

## 2. BM25 的缺点是什么？
BM25 更依赖关键词匹配，对语义级召回不如 embedding 检索强；当用户问题和文档表述差异较大时，召回效果可能下降。所以它更适合做轻量原型或作为混合检索中的一部分。

## 3. 你这个项目最大的技术问题是什么？
一个是真实的分块问题。固定长度切分会把词和句子切断，导致检索结果虽然“命中”，但可读性和可信度很差。另一个是生成阶段的超时问题，所以我后面加了 timeout、重试和失败兜底。

## 4. 为什么来源引用很重要？
因为 RAG 的价值不只是“回答出来”，还包括“让用户知道答案依据了什么资料”。来源引用一方面有助于调试召回质量，另一方面也能提升系统可信度，尤其适合求职展示和演示场景。

## 5. 这个项目如果继续做，你会怎么升级？
我会优先做三件事：第一，把 BM25 升级成混合检索或向量检索；第二，加多轮对话记忆和问答历史；第三，把项目容器化并部署成一个可访问的在线 Demo。

## 6. 这个项目体现了你什么能力？
我觉得主要体现了四点：第一，能从零搭建 LLM 应用链路；第二，能根据环境约束做技术取舍；第三，能把功能做成 API 和前端页面；第四，能把项目整理成适合展示和迭代的工程结。
