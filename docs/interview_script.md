# 项目讲解稿

## 30 秒版本
我做了一个轻量级中文 RAG 项目，目标是在不依赖本地重型向量模型的情况下，先完整打通“检索 + 增强 + 生成 + 服务化 + 展示”链路。项目使用 BM25 和 jieba 做多文档检索，使用 OpenAI 兼容接口完成答案生成，同时保留来源引用、查询日志、FastAPI 接口和 Gradio 页面，适合作为 RAG 工程化入门和求职展示项目。

## 1 分钟版本
这个项目的核心目标是实现一个低环境成本、但链路完整的 RAG 原型。我的做法是先把 knowledge 目录下的多个文档加载进来，按段落优先进行分块，避免固定长度硬切带来的语义断裂。然后用 jieba 分词和 BM25 做召回，把 top-k 片段连同 source 和 chunk_id 一起拼进 Prompt，再调用 OpenAI 兼容接口生成最终答案。为了让这个项目更像一个真实应用，我还补了 FastAPI 接口、Gradio 页面、查询日志记录以及来源展示，这样既能方便调试，也更适合在 GitHub 和面试中展示。

## 3 分钟版本
这个项目一开始并不是追求最强的检索效果，而是追求在我当前环境约束下，先把一个完整的 RAG 系统做出来。我最初尝试过更重的本地 embedding 路线，但会带来额外的 torch 和 CUDA 依赖，环境成本很高，所以我后面主动调整方案，先用 BM25 搭一个轻量原型。这样做的好处是可以先把 RAG 的主链路吃透：文档加载、文本分块、检索、上下文增强、答案生成、服务化和展示。

在实现过程中，我碰到过两个比较真实的问题。第一个问题是分块质量。最早直接按固定字符长度切分，会出现从单词或句子中间切开的情况，虽然程序能跑，但检索结果可读性很差，引用展示也不可信。后面我把分块策略改成按段落优先切分，并为每个片段增加 source 和 chunk_id，这样检索结果和最终答案里的来源引用都更清晰。第二个问题是生成阶段的接口稳定性。有些查询会遇到超时，所以我在生成模块里加了 timeout、重试和失败兜底逻辑，避免整个 CLI 或 API 因为单次生成失败直接崩掉。

最终这个项目支持三种使用方式：命令行、FastAPI 和 Gradio。命令行适合快速实验，FastAPI 方便后续对接服务，Gradio 适合展示给别人看。对我来说，这个项目最重要的价值不是某个单点技术，而是我把一个 LLM 应用从“概念”真正做成了“可运行、可调试、可展示、可上传 GitHub”的工程项目。
