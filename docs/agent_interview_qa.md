# Agent 项目面试问答

## 1. 这个项目和普通 RAG 有什么区别？

普通 RAG 主要是“检索 + 生成”，用户提问后系统从知识库检索相关片段，再调用大模型生成答案。

这个项目在 RAG 基础上加入了 Agent / Workflow 思路。系统不只会问答，还能根据用户请求选择不同工具，例如知识库问答、文档总结、文档对比和澄清节点。它更像一个多工具工作流系统。

## 2. 为什么先做 Workflow，而不是直接做开放式 Agent？

因为 Workflow 的执行路径更可控，更适合学习和工程落地。  
当前项目目标不是让模型完全自由规划，而是先把路由、状态、工具调用、错误回退和记忆机制做清楚。

开放式 Agent 虽然更灵活，但也更容易不可控。  
所以我先实现一个可控工作流，再逐步向更开放的 Agent 过渡。

## 3. LangGraph 在这个项目里解决了什么问题？

LangGraph 主要解决了状态流和节点编排问题。  
在这个项目中，每个节点只负责一件事，例如路由、执行 RAG、总结文档、比较文档、澄清请求和汇总结果。

所有节点通过共享 state 传递信息，使整个流程比简单 if/else 更清晰，也更容易扩展。

## 4. 你为什么要设计 Clarify 节点？

因为用户请求经常是不完整的。  
例如用户说“请总结那个文档”或者“比较这两个文档”，如果系统直接猜测，很容易调用错误工具或产生不可靠结果。

Clarify 节点的作用是：当参数缺失或指代不清时，不盲目执行，而是要求用户补充信息。  
这能提升系统稳定性和可信度。

## 5. 多轮记忆是怎么做的？

项目中通过 LangGraph 的 checkpointer 和 thread_id 管理短期记忆。  
同一个 thread_id 下，多轮对话会共享历史 state，系统可以根据最近几轮记录理解用户后续请求。

例如第一轮用户让系统总结 engineering.md，第二轮说“再把它压缩成 3 条”，系统可以结合历史判断“它”指的是 engineering.md。

## 6. 当前项目有什么局限？

主要有三个局限：

1. 目前工具种类还比较少
2. 路由依赖大模型输出，仍然可能出错
3. 记忆是短期记忆，当前版本还没有接数据库持久化

后续可以继续升级为：

- 更强的工具集
- 更严格的结构化路由
- 数据库持久化记忆
- 更完善的 Web UI
- Docker 部署

## 7. 如果继续优化，你会怎么做？

我会优先做三件事：

1. 把路由输出进一步结构化，减少模型自由发挥
2. 加入持久化存储，让历史记忆不随进程关闭而消失
3. 把 RAG 检索从 BM25 升级为混合检索，提高召回效果
